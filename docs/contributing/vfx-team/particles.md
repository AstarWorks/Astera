## Founder bar

Founder 2026-10-24: "Display builds the VFX core; particles reinforce it for polish and presence. TextDisplay custom particles have far too little expressive power vs vanilla; the reason is that the foundation isn't built. Accumulate knowledge: a dedicated agent."

Consequences: the core always comes from `vfx-artist`; particles are attached to a core element and never substitute for it; vanilla first; the custom-particle foundation is a long-running goal tracked below.

Consequences: the reference governs pose, timing, camera and the large forms only. Particles are free design from the skill concept: choose the type, emission point, count, speed, spread, lifetime and colour for good looks in Minecraft, without copying Limbus frames. Anchor them to the animation and the weapon: blade tip / edge trail along the rig path, the contact point, the dash vector, the landing. The round note's "Medium" section carries a `particle concept:` line per beat (intent, anchor, params; gate-checked, [round-template.md](round-template.md)); the reviewer judges whether they look good and read as motion-linked, never resemblance to the reference.

Cross-cutting facts:

- A particle file has no lifetime field (the dead `lifetime_ticks` was removed, ADR-0312): the client decides life per type (rows above).
- Vanilla particles carry no per-particle colour/size/alpha except through `data` (dust family, `power`, etc.).
- Direction by the `count=0` trick (offset becomes velocity): technique T-18 in [minecraft-techniques.md](../../reference/vfx/minecraft-techniques.md); for vanilla particles it is **unconfirmed** there. The particle file exposes `velocity {direction, speed, spread_degrees, custom}` instead; record in the Learnings log how the runtime maps it before relying on it.
- A plain spread is the vanilla `offset: [x, y, z]` (world axes); sampled shapes (`shape.kind`: `line`, `circle`, `sphere`, `ring`, `arc`, `helix`; fields `radius_blocks`, `points`, `from_deg`, `to_deg`, `length_blocks`) are in `content/schemas/particle.schema.json`; `viewers` and `force` are there too.

## Techniques

- **Layer on the core**: each particle batch anchors to one core element (sweep tip, flash centre, ring edge, hit point, ambient anchor) and starts on that element's beat tick; the core must read alone with the particles removed.
- **Arc / ring sampling**: sample points along the swept arc or ring (`shape` arc/ring fields, or one particle file per sampled tick) so particles follow the silhouette instead of clouding the origin.
- **Ride a weapon rig: read the path, never copy keys** (r24). `tools/item-art/scripts/rig_path.py` reads the rig (`content/vfx/<rig>.yaml`: pivot, tilt, rest, swing keys + eases, `respect_hit_stop`, parts) and the skill (`content/skills/<skill>.yaml`: the `play_vfx` delays of the rig and of your fx file, the rig's `freeze` windows, every `dash_strike`) and reproduces the runtime's `VfxRigMotion` (chunking, slerp, hit-stop clock, `follow`/`attach_to_anchor` riding the dash) in the fx file's own frame. Usage from any generator:
  ```python
  from rig_path import RigPath
  rp = RigPath("<skill-id>", "<rig-vfx-id>", fx_vfx="<fx-vfx-id>")   # rig_id=... if the file has several rigs
  for start, contact, resume, end in rp.strike_windows():  # r25: strike only (starts after the last hold / turn), coil excluded
      for t, p, tangent in rp.arc(start, contact, radius=2.3, step=0.4):  # points on the TRUE arc, fx ticks
          ...  # emit at int(ceil(t)) at p, direction from tangent
  c = rp.blade_point(contact, radius=1.5)   # contact anchor; rp.target_eye() = opponent eye at the dash stop (DISTANCE 4)
  ```
  CLI table for briefs/evidence: `python3 tools/item-art/scripts/rig_path.py <skill> <rig-vfx> <fx-vfx>` (per fx tick: skill tick, rig tick, tip position, phi/pitch, tip speed). Re-run the particle generator after every rig or skill-timing change; nothing else needs editing. Sample the arc, not keyframe chords: a 120 deg one-tick chunk's chord passes ~1.1 blocks from the pivot, through the caster. Example consumer: `bastion_s1_particles.py` (`ring_sheds`, `ring_embers`, `hit1`, `hit2`). **Window start = where the strike begins, never the first fast tick** (r25): `strike_windows()` walks back from the contact and stops at the last hold (tip < 0.5 blocks/tick) or the last turn (blade rotation axis `spin_axis()` > 60 deg off the axis entering the contact). `swing_windows(min_speed)` is speed-only: a fast drop into a coil (1.3-3.2 blocks/tick) passes it, so do not use it for emitters.
- **Stagger**: few particles per tick spread across several ticks, no overlapping positions (Sakurai: few and clever; [vfx.md](vfx.md) principle 4).
- **Dark + bright**: pair every bright spark/ember with dark smoke/chips; use `dust_color_transition` bright -> dark for embers.
- **Short and small**: dust at scale 0.35-0.5 for sparks (life ~5-20 ticks); big counts only far from the caster camera.
- **Ground impact**: debris up, a short ground poof at the contact tick, dust specks; keep it below camera level for the caster view.
- **Volume goes into vanilla particles**: Display elements are budgeted (<= 60 per cast, <= 40 per element, ~16 per fx); a heavy hit affords about 10 sprites and 4-6 display particles.
- Display particles (`emit` on quads: flat squares) are a last resort; see [vfx.md](vfx.md) for the quad calibration. `size_over_life` / `alpha_over_life` / `color_over_life` / `spin_over_life` are multi-key curves (`[{ t: 0..1, v, ease? }, ...]`, any number of keys, `t` ascending; ease applies to the segment ending at the key). Example: `size_over_life: [{ t: 0, v: 0.2 }, { t: 0.15, v: 1, ease: out_quad }, { t: 1, v: 0 }]`. Sprite elements can emit too (`start_frame: random | <int>`, `frame_ticks: [min, max]`); `color_over_life` is quad-only.

## Custom-particle foundation

Status: **P1 built (route A)**, [ADR-0274](../../adr/0274-particle-foundation-retextured-vanilla-particle-channels.md). A channel = a vanilla particle type whose sprite list the resource pack replaces with hand-drawn smooth frames (`content/particle-skins/<type>.yaml` -> `:tools:item-art` -> `content/particle-skins/generated/` -> pack). Motion, lifetime and billboarding stay vanilla ("every tick looks different"); only the picture is ours. The display core (ADR-0239/0220) stays for hero shapes; routes B (shader) and D (animated item display) are deferred.

| Channel | Vanilla type | Tint | Frames | Behaviour of the type (26.3 client jar) |
|---|---|---|---|---|
| `ember` | `entity_effect` | grey; server colour via `color` | 8 | translucent; rises (gravity -0.1, friction 0.96), vertical velocity x0.2, life 10-40 ticks; texture must fade itself (no fade in the type) |
| `spark` | `firework` | baked | 32 (0-7 drawn, rest clear) | white multiplier; velocity kept, friction 0.91, gravity 0.1; life 48-60 ticks, so the visible part is the first 8 frames (~12-15 ticks) |
| `smoke` | `cloud` | baked grey | 12 | translucent; grey multiplier 0.7-1.0 per particle; life ~18-66 ticks; pulled toward a player within 2 blocks |

Authoring a channel: add `content/particle-skins/<vanilla-type>.yaml`, add/extend a painter in `ParticleSkinPainters.kt` (continuous colour + alpha field, transparent border), `./gradlew :tools:item-art:run`, look at `docs/assets/particle-skin-preview.png`, commit the generated files. Pick a type that (1) picks its sprite by age, (2) renders on the TRANSLUCENT layer when the art needs soft alpha (the `smoke`/`large_smoke`/`white_smoke`/`poof`/`explosion` and `electric_spark`/glow families are OPAQUE: binary alpha only), (3) has a neutral or known colour multiplier, (4) is not used by vanilla gameplay Astera players see. A reskin is server-wide for that type; `contentLint` lists the Astera particle files that use each skinned type.

Emitting 30-100 moving particles per contact costs no display: a `kind: particle` fx element (`start_tick..end_tick`, `every_ticks`) plays a particle definition whose `count: N`, `velocity: {direction, speed, spread_degrees, speed_jitter}` and `shape` plan N particles per call through the `count = 0` directed-particle trick. Demo: skill `vfx-demo-particle-skins` (`content/vfx/demo-particle-skins.yaml`, `content/particles/skin-demo-*.yaml`).

v2 `emit` (SKL-15, 2026-10-28): an `emit` op of a custom particle id with `count: N` plans exactly N particles (the definition's own `count` is replaced, not multiplied); unset keeps the definition's. A shaped definition with no `dir` faces `look(caster)` (full yaw and pitch). A vanilla key maps 1:1 to `spawnParticle(count, offset, extra, data)`; see [add-a-skill-yaml.md](../add-a-skill-yaml.md) "emit は vanilla の spawnParticle そのもの".

## Craft checklist (P-numbers: [pixel-vfx-craft.md](../../reference/vfx/pixel-vfx-craft.md))

- **Heat budget (P5).** Particles are accent or ambient: mid-ramp colours, at most two hue families plus smoke; the hottest band belongs to the core. Pair bright with dark ([Dark + bright](#techniques)).
- **Bands (P1).** `color_over_life` / `dust_color_transition` move down the ramp in steps; no soft alpha-ramp glow.
- **Break up, do not shrink (P3).** In dissipation, particles spread and cool; do not run `size_over_life` to zero as the only ending. Smoke starts late (about a fifth in).
- **Ground (P8) and loops (P9).** Ground poofs start at the floor line; periodic emitters complete whole cycles.
- **Culling (P2).** Particles must be removable (`lane: accent` / `ambient`) without losing the shape.
